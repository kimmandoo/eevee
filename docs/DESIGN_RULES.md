# Eevee Design Rules

Status: the party model (one or more partners, free switching, cooperation) is a confirmed contract whose implementation is pending; the local runtime implements artwork/navigation, durable task lifecycle/privacy/quotas, repository/source evidence, approved owned commands/recoverable journals, preflight, Codex Plan/controlled Implement, optional official Claude SDK, shared ACP1 OpenCode/Gemini/Devin and version-1 handoff. The user has authorized public 0.1.0 release, binary installation/update/uninstall, commit and push. Fresh five-row native qualification gates publication; the historical billing/deferment state is superseded. A04/A06/full A07 remain authentication-blocked; implemented adapters are not claims of full provider conformance.

Implemented B/C boundaries: context exclusions conservatively match case-folded path components without merging file/project identities; assembly revalidates source containment/content and persisted references. Payload previews show exact serialized bytes and a labelled bytes/4 token estimate, not a provider's effective prompt. Task-row export is not an evidence backup. Metadata deletion can commit while physical cleanup fails: report the committed scope and cleanup warning, never a fictional rollback. Below-minimum terminals must retain neutral owned-work cancellation while refusing command approval until the complete review surface fits. Restored nested overlays and search retain their input ownership.

Implemented A02 boundaries: only explicitly reviewed Codex 0.152.1 Plan turns can dispatch. Task revision/committed basket, source scope/content and executable/known configuration identity are revalidated immediately before dispatch. The app-server acknowledges read-only/user-approval policy; this is provider-controlled, not an Eevee sandbox or universal interception of provider tools/hooks. Questions and command approvals are generation/thread/turn/item/request-correlated; only one-time offered decisions are allowed, and cancellation invalidates stale responses. Each explicit turn owns its transport; no automatic reconnect/resend or restored grant. A selected complete plan/message becomes durable only through the ordinary reviewed Next action editor, retaining provenance and unverified status.

Implemented D boundaries: Codex existing-file replacement uses a reviewed dirty baseline and exact deny/allow-once patch; anchored POSIX enforcement rejects protected/unselected/link/stale paths without promising containment of independent provider tools. SDK mandatory tools/config controls are separate from callback approval; selected SDK writes are explicitly external policy. ACP fs/terminal callbacks are unsupported/refused, agent-owned effects remain external, and optional methods require actual negotiation. Capability/session-list inspection never dispatches a model or authorizes an unknown session. Schema-5 provider journals are append-only observations with origin/coverage, not local command evidence. Storage failure retains records for storage-only retry. Reviewed schema-1 handoffs omit sessions/grants/private reasoning/credentials; imported claims stay unverified and stale dispatch bindings fail closed.

Implemented authentication boundary: local tasks never require an account. Connection discovery, version probing, explicit official login/status and model submission are separate actions. Login reviews disclose provider-owned browser/network/credential/configuration effects, require 80×24 and committed idle state, and lend/restore terminal ownership. Codex browser/device OAuth and OpenCode's native provider chooser are available. Gemini 0.28.0's mixed interactive/ACP auth output requires explicitly labelled external native CLI handoff: choose Google OAuth/browser/manual-code, API key or Vertex there; its CLI may continue into chat, but Eevee sends no task/prompt and does not collect authorization codes. No task is replayed afterward. Claude SDK never reuses claude.ai subscription OAuth; permitted API/cloud routes include separately opted-in provider-managed SSO/ADC chains. Unconfirmed authentication/cancellation stays unknown, and fresh login cannot erase a prior unresolved outcome.

Devin CLI 3000.11.3 adds dedicated native browser OAuth and explicitly selected manual-token login, with provider-owned status output. Tokens and credential stores never enter Eevee. Login/status exit alone remains unknown; task submission requires separate approval. Its local ACP agent retains the shared external-tool boundary, with managed Review and controlled implementation refused. A separate Eevee-owned website OAuth route (authorization-code + PKCE against server.codeium.com, loopback callback or pasted redirect) returns a Windsurf session credential that exists only in process memory: it is never serialized, journaled, logged or shown, Debug output is redacted, and the bytes are scrubbed on drop. Eevee injects it into the launched `devin acp` child's environment as WINDSURF_API_KEY only; it takes precedence over the CLI's stored credentials, expires from the JWT exp claim minus a five-minute skew, and any expiry is disclosed as a launch blocker on the next review. A native Devin CLI login clears the in-memory credential on success.

First-use contract: the primary composer accepts text immediately. Goal Enter saves locally with a short notice; the action chooser opens only from `/` or Ctrl+K. Dispatch still needs a separate reviewed Run. Provider/model/role selection has explicit context popups, disabled prerequisites and no implicit request. Old letter/digit/F-key actions are removed. Commands preserve drafts and caret/suffix; pasted slash text never invokes navigation. Artwork has separate reviewed download/reload actions; opening a form stays offline.

Implemented E/F boundaries: schema 6 preserves task-local hypotheses, bounded refactor contracts/baselines, evidence-linked findings, guarded review verdicts and recipe plans/drafts. A supported diagnosis requires explicitly linked current source and run observations; failed diagnostics remain actual failures. Comparisons require distinct ordered complete passing runs of the same command/cwd/executable and current post-change identity; a single elapsed-time pair is not a speedup claim. Review uses freshly revalidated requirements/patch/selected observations, not implementation history or imported handoff; managed Review has no Resume/write grants, and ACP Review is refused. Accept is re-evaluated against current criterion evidence rather than trusting its persisted label.

Curated memory and recipe consent: approved task/project/personal notes use the existing single SQLite writer. Scope/provenance/content are previewed, approval is neutral, and outgoing selection is separate; dispatch revalidates exact selected identities/revisions and deletion removes future context without claiming historical erasure. Task deletion preserves project/personal records. Strict schema-1 local TOML recipes may stage a plan/criteria/context proposals/validation argv only; unknown capability fields cannot grant authority. Documentation writes keep their own preview/approval. Specialist editors retain grapheme-safe drafts and refuse affirmative operations below 60×18.

## Product

Eevee is a local-first terminal workbench for LLM-assisted development. Your own party of Eevee partners retains the task, evidence, and decisions while specialized forms expose the right tools; each partner switches form freely, and several partners may cooperate on one task. It is not another full-screen chat log or nine permanently running agents: idle partners do nothing and cost nothing.

Use Eevee and its eight existing evolutions; do not invent additional species. Species and types follow the original concept. Software responsibilities below are product interpretations, not claims about canonical abilities. Forms are reversible workbench states, not a simulation of the games' evolution restrictions.

### Experience: a partner, not a themed dashboard

- **Sanctuary** is Eevee's home: one active task card, its completion criteria, and one recommended next action. With no task, show one invitation to create a goal, not nine empty specialist dashboards.
- **Partner** is one individual Eevee in the user's party: nickname, current form, met date and, later, its own learned moves. The lead partner is the one in front of the current task; other partners may be idle or working on the same task.
- **Evolution** changes the tools for the same task. Keep the task identity, selected evidence, decisions, and user-approved scope across forms. The role is independent of the selected execution agent/model; changing either selection does not itself submit a request.
- **Field journal** is the task's inspectable evidence history: observations, decisions, executions, reviews, and handoffs. Cosmetic form selection is not evidence. Opening the journal performs no model call.
- **Bond** means explicitly approved project/personal habits that save repeated instructions. No affection score, XP, hunger, streaks, random unlocks, or inaccessible forms.
- **Evolution Stones** are task recipes, not collectible currency. All nine forms remain locally selectable; recipes do not imply every canonical species evolves through a stone.
- Keep original species names/types and visual cues, but use plain developer verbs for actions. Do not rename a failing command as a successful “attack” or conceal errors behind character dialogue.
- The companion is a small upper-right accent, not a full-height dashboard column. Personality comes from the original species sprite, restrained elemental UI accents, and factual status. Never insert unsolicited chat or interrupt execution with an animation.

### First useful journey

1. Open Eevee, create a bounded task, and define what would count as done.
2. Select Vaporeon to inspect relevant code and pin source ranges into a context basket.
3. Select a specialist for the actual problem: Espeon for a design choice, Umbreon for a failure hypothesis, or Flareon for an already-scoped change.
4. Inspect a handoff card before any model request or command: goal, selected context, allowed scope, requested action, and expected result.
5. Let Jolteon run an explicitly approved verification. Glaceon then reviews the patch against the requirements and the observed result.
6. Sylveon prepares a source-linked handoff. Closing/reopening returns to the same task and unresolved next action, not a fresh chat.

This is a route, not a mandatory tour through every form. Skip irrelevant forms; never issue model calls just to fill a progress trail. The smaller local-only milestone is create task -> exit -> resume -> inspect sources; it must be useful before a provider is connected.

These defaults define requested workflow scope, not proof that a tool or subprocess is confined. An arbitrary approved command can have unknown effects. The selected profile must establish each claimed restriction at the real boundary; otherwise the controlled action is unavailable or explicitly external, never silently treated as read-only.

### Boundaries

- Eevee routes; Espeon designs. Intake must not silently become an architecture exercise.
- Vaporeon gathers context; Umbreon tests explanations of a failure or risk.
- Flareon changes behavior; Leafeon improves structure or efficiency within an agreed behavioral contract.
- Jolteon records execution, not correctness judgments. Provider-native tool runs may be observed in its journal without being launched by Eevee; never duplicate them to simulate control. Glaceon judges evidence and never silently fixes its own findings.
- Sylveon records verified conclusions, not invented success or inferred user preferences.
- One active form per partner. An idle partner switches form freely and instantly; switching is local UI/state work and must not trigger a model call by itself.
- Form changes require deliberate selection (picker Enter, a named form command or the previous-form toggle) or acceptance of a recommendation. No confirmation dialog is required, and a switch never grants additional permissions.
- Shared state does not imply shared prompts: specialist requests contain only relevant evidence and constraints.
- Independence in Glaceon means a separate review context with the requirements, patch, and observed evidence; it does not imply a different model or guaranteed correctness.

### Party

Status: PT02–PT05 shipped the party store, roster/add, direct lead selection, named form switching and per-(task, partner) drafts/carets. Schema 8 enlarges Schema 7's reserved draft column to preserve all previously valid escaped text for six partners. Existing task drafts transfer to their lead; the composer names its owner and draft-discard decisions affect that draft only. Until PT06/PT07 ship, the runtime allows one working request.

- **Size:** up to **6** partners in the party. A new partner starts as Eevee. Releasing a partner deletes its moves and pairings but never its evidence; evidence keeps a name snapshot of the partner that produced it.
- **Concurrency:** up to **3** partners may work on one task at the same time. Each partner owns its own draft, requests, approvals, questions and cancellation. Every journal entry, provider event and approval carries (task, partner, request); a late or stale event is never routed to another partner.
- **One writer:** edit-capable work (Flareon, Leafeon) takes a per-task write lease. Another partner's edit waits; a run started while the lease is held is recorded as `revision moving` and is not fresh verification. The lease is released on completion, cancellation and crash recovery.
- **No autonomy:** partners never start work on their own and never trigger another partner's work. Handing work to a partner pre-fills its draft with references only: no approvals, sessions or grants move.
- **Visible cost:** each provider request keeps its own review and receipt; cooperation never merges or hides per-partner cost.
- **Review independence:** a Glaceon review by a partner other than the patch author is preferred; the same partner is allowed and labelled `same partner`.
- **Flavor stays local:** nicknames, partner names and dialogue never enter provider packets or handoffs.

An action card distinguishes three operations: local navigation (no model call), a provider request (selected context leaves the process), and a command/write operation (capability check). Display unavailable prerequisites with a reason, not a working-looking button. A running request keeps its owning partner and form; that partner changes form only after completion or explicit cancellation, never an implicit cancel. Another partner may be brought to the front instead (see Party).

### Role, agent, model, and control are independent

- A form answers **what are we doing?** An agent profile answers **which external program performs it?** Its model and permission mode are separate, agent-advertised choices. Espeon is not automatically a provider's “plan mode,” and Glaceon is not a particular vendor.
- Show requested provider/model/effort/role separately from the observed session model, without recoloring the companion. Opening model/effort pickers is local and never spawns a provider. Explicit catalogue refresh requires ordinary executable/configuration/network-effects review; model selection must be applied and acknowledged by the official interface before prompt submission, or fail with a capability reason.
- Capabilities are action-specific: structured output, approval/questions, cancellation, same-agent session loading, tool limits, filesystem/network policy, and usage may differ. Missing or unknown support is not permission. Disable only the affected action, explain why, and keep local browsing/notes/review available.
- An approval callback is not an OS sandbox. Distinguish **Eevee-mediated**, **agent-policy-controlled**, and **observed/unmanaged** effects in the inspector and request preview. Label restrictions by the actual mechanism/scope, not a single reassuring “safe” badge.
- During a request, users may browse existing evidence and edit a future draft, but changing the working partner's form/agent/task requires completion or an explicit cancel-and-wait transition. Offer Stay instead; never transfer a running request's ownership. Preserve per-task drafts and never route a late approval or streamed event to another agent/task.
- A new agent receives a user-reviewed handoff, not the old agent's opaque session ID, private reasoning, credentials, or assumed memory. Same-agent resumption is separately verified against agent version, cwd, context/config identity, and policy. Fresh Glaceon review context remains separate even when the same agent is reused.
- The outgoing context basket describes **what Eevee sends**, not necessarily the whole effective model input. Agents may load project rules, hooks, history, plugins, MCP tools, or additional files. Inspect or disclose those sources where possible; if they cannot be bounded, do not promise complete context isolation or hard read-only operation.
- Before connecting, distinguish provider-owned authentication/billing, project executable configuration, and persistent trust/configuration effects. Do not import credentials or mutate global settings to hide a missing prerequisite. Provider-owned side effects such as a persistent trust change require explicit preview/consent, not a form selection.
- Readiness is specific to agent version, native OS, and requested action. Discovering an executable candidate is not permission to execute it: repository-supplied candidates require explicit trust before even a version/preflight invocation.
- Adapter transports, evidence levels, request/event semantics, and per-agent limitations are specified in [Agent compatibility](AGENT_COMPATIBILITY.md).

### Navigation and editing

- Persist navigation position per task/surface: selected file/finding, scroll anchor, open drawer, and draft. Resizing hides panes without losing their state; closing an overlay restores its invoking control when it still exists.
- Literal command/source/search/question editors own character input; pasted slash text never invokes an action. The primary Goal composer permits an isolated slash-command popup without altering its draft/caret/suffix. Enter applies Goal locally; committed storage acknowledgment is required before preparing a provider request. Every dispatch still requires its request-preview Run, never generic Enter or a pasted newline.
- Support grapheme-aware cursor movement/deletion, Home/End, multiline paste, Unicode display width, and horizontal/vertical reveal of the caret. Do not interpret pasted slash commands as application navigation; agent commands are separately labelled and sent only through the chosen agent.
- Slash choices expose capability prerequisites and current scope. Recheck context, task/save/busy state and terminal size at dispatch, not just menu construction. Disabled actions explain the missing prerequisite. Local model picker state is not active provider work, but catalogue refresh still needs committed input and separate connection consent. Switching models invalidates prior payload consent and offers Keep current / New session / Back for incompatible owned sessions.
- Live output follows the end only while follow mode is enabled. Manual scrolling pauses follow; a visible “new output” indicator offers a deliberate jump. Search highlights and selection stay stable as output arrives; virtualize large lists/diffs and do not repaint the full history per chunk.
- Links, clipboard actions, and launching an external auth command require a deliberate user action. No OSC 52 clipboard writes from tool output. Sanitize terminal escape sequences while preserving useful plain output; keep structured content separate from rendered text.
- Before discarding a changed editor draft, offer an explicit discard decision; unchanged drafts need no extra confirmation. Label the distinction between leaving an editor and closing a still-pending request view. Below minimum terminal size, preserve drafts/run state and expose safe quit/cancel; resizing must not trap the user or implicitly approve/discard work.

### Approval and agent-question UX

- One correlated queue holds pending requests with task, run, agent/profile, tool ID, and approval/question ID. Requests may coexist, but only the deliberately opened item owns focus. A question is not a permission grant; do not combine the two.
- Opening a request focuses its details, not Allow. Show exact command or diff when supplied, cwd/path scope, unknown effects, requested duration, and who enforces the decision. Navigation or repeated Enter on the neutral initial control must never approve.
- Offer only semantics actually supported by the adapter. An agent's `allow_always` is not automatically “allow for this Eevee task.” Broad/persistent options require explicit scope disclosure; hide them if their duration or boundary cannot be represented accurately.
- Revalidate before responding. If tool inputs, profile/config, run generation, or scope changed, invalidate the old answer and show the updated request. Expired or already-resolved requests are read-only; answering twice cannot dispatch twice.
- Esc returns to work while the request remains pending; explicit Reject responds with rejection, and Cancel run resolves pending requests with the protocol's cancellation semantics. Never remember an allow merely because a form or model was chosen.
- Agent forms preserve field values/errors, offer the provider's real choices plus supported free text, and let the user decline when the protocol permits. Do not invent answers for unsupported question schemas; report the limitation and keep the user in control.

### Operational, persistence, and evidence states

- Track independent state axes rather than one overloaded badge:
  - Task outcome: open, complete, cancelled.
  - Request: idle, connecting, running, awaiting permission, awaiting input, cancelling, succeeded, failed, cancelled, disconnected/outcome unknown.
  - Storage: draft, saving, saved, save failed.
  - Evidence: current, stale, ambiguous, unavailable.
- Priority in a compact header: safety/pending input, failure/unknown outcome, unsaved state, active work, then idle readiness. Secondary state remains available in the inspector. Color accompanies text; provider/model names and task identity never disappear behind decorative art.
- Show “working” with an actual last-event indicator, not invented percent complete, hidden-reasoning text, or a success animation. A quiet connection is not automatically a hung run. “No recent updates” offers inspection/cancel without claiming failure.
- A disconnect retains the partial journal and marks outcome unknown when completion is unobserved. Reconnect/resume is explicit and never replays a mutating request automatically. Reconcile already-applied changes before offering a new attempt.
- Save failures remain visible and retain recoverable draft content. On quit/switch, offer explicit retry-save, stay, or discard-unsaved choices; never present an unsaved task as durable. A provider-local session may persist independently and must not be confused with Eevee's own save result.
- Durable storage has an explicit schema/version and one writer. Detect another writer and expose the conflict without silent takeover. Migrate older schemas transactionally with a tested rollback/recovery path; never overwrite a corrupt or newer-schema database. Disk-full and locked-database failures retain the editable draft. Only a committed revision may be acknowledged as saved, and late acknowledgments must never regress the saved revision or label a newer draft saved.
- With active work, quit and Ctrl+C open a neutral-focus Stay / Cancel-and-exit decision, not an immediate process kill. Cancel-and-exit waits for acknowledgment or verified owned-tree exit with bounded escalation; unconfirmed teardown remains outcome unknown. Repeated keys must not accidentally confirm or force-kill. Unsaved-state choices still apply, and neither cancellation nor exit promises file rollback.
- Error cards identify layer and remedy: image loading, local storage, agent executable, auth, capability/version, transport, model request, permission denial, or command exit. Preserve technical details behind an inspect action; transient notices do not erase the selected artifact or steal focus.

### Accessibility and visual quality gates

- Keep a linear text/activity layout with the same actions and state labels; portraits are optional, never the only identity/status signal. Do not claim screen-reader compatibility before exercising a real assistive terminal setup. Reduced visual detail does not reduce approval controls or evidence.
- For the application's own true-color themes, target at least 4.5:1 text contrast and 3:1 focus/control contrast; verify selection, errors, muted text, and both backgrounds. Unknown user terminal palettes require monochrome/reverse/focus-marker fallbacks, not an unmeasured contrast claim.
- No blinking, animation-dependent meaning, mandatory icon font, or color-only distinction. Truncate display paths/titles with a visible continuation affordance; inspection reveals exact values before approval. Never truncate the only visible executable or affected scope without an expansion control.
- Run actual TUI scenarios across the supported size/theme matrix: first-run empty, missing agent/art, loaded task, long CJK draft, pending permission/question, large streaming output while scrolled, cancelled run, save failure, stale review, provider switch, and return after interruption.
- User-success criteria: a new user can find the next action without opening help; can identify active task/form/agent and control limitations before sending; cannot execute by navigation/paste; can stop work and recover their draft; can explain why a result is or is not verified. Record observed scenario outcomes, not subjective “looks polished” alone.

## Task and evidence model

A task owns its goal, acceptance criteria, current form, agent-profile selection, independent request/storage/evidence state, decisions, source references, changes, executions, findings, permissions, and handoff. Forms exchange a compact envelope: goal, scope, evidence references, unresolved items, requested action, and completion condition. Provider session references are profile-scoped and never portable grants.

Separate observed facts, model inferences, and user decisions. Persist provenance for each. A command result contains cwd, sanitized arguments, start/end time, exit/signal status, output references, and before/after code-state identities. A passed command is not proof of every requirement.

Capture the initial working tree without overwriting user changes. Git metadata and baseline file identities distinguish pre-existing changes from session changes; concurrent external edits remain unattributed rather than falsely assigned to the agent. A code-state identity covers relevant tracked and untracked inputs, not only HEAD. Changes during a run make its association ambiguous; changes after a run make its verification stale. Display unknown coverage explicitly.

Legacy Phase 1 surfaces use a simple ready state. Planned task/request/storage/evidence axes are defined above; task completion is separate from request success and requires the explicit acceptance checklist plus visible unresolved risks.

### Task lifecycle and local retention

- Completion requires an explicit state transition. Changing the goal or acceptance criteria of a completed task requires deliberately reopening it; an old verdict must not imply the new criteria passed.
- Archive hides a task without deleting its evidence. Delete/purge is separate: preview the affected task records, drafts, output/assets, and shared references, then require confirmation with neutral initial focus and a no-effect Cancel path. Do not purge active work or silently sever its evidence.
- Redact identifiable credentials before any metadata, journal, or output-spool persistence; do not promise perfect detection. Provide configurable spool quotas and retention with visible disk-pressure behavior. Never silently evict active evidence; when capacity is exhausted, stop further capture/execution safely and expose the limitation rather than recording complete evidence.
- Retention and explicit deletion must show missing artifacts as unavailable, not empty or successful results. Preserve memory/profile records still referenced by other tasks; task deletion is not blanket shared-state deletion. Explain local scope: purge is neither secure erase nor deletion of provider-owned sessions/data. Command runners and durable-memory flows inherit these rules.

## Permissions and recipes

- Capabilities are enforced at the execution boundary, not merely described in prompts.
- Reading, writing, command execution, network access, and durable memory are separate capabilities. An external CLI without enforceable restrictions must be labelled unmanaged; do not present it as sandboxed.
- Approvals show exact arguments or shell text, cwd, affected scope where known, and permission duration. Unknown command effects remain unknown.
- Imported recipes are untrusted configuration. Loading one neither runs commands nor grants permissions.
- Evolution Stones are versioned TOML recipes specifying form workflow, allowed scope, context selection, validation commands, and completion criteria. A recipe cannot widen existing grants.
- Memory is task-local, project-local, or personal. Promotion to project/personal memory requires explicit approval and supports inspection, editing, and deletion.
- Treat terminal output, repository text, and external sources as untrusted content. They cannot modify grants or issue application commands. Strip unsafe terminal control sequences before rendering.

## Implementation stack and efficiency

Choose Rust with Ratatui and Crossterm for the native TUI, Tokio for asynchronous I/O and subprocess coordination, Serde for schemas, TOML for recipes, and SQLite through rusqlite for durable task metadata. Store large command output in bounded/rotated local files referenced by metadata. Begin with one Cargo package and explicit modules, not a multi-crate framework.

Rust offers native startup, predictable memory ownership, and no garbage-collector pauses. This is a fit-for-purpose decision, not a claim that any language is universally fastest. Model/network latency will usually dominate agent work; reducing unnecessary context and calls matters alongside rendering efficiency.

The planned Claude Agent integration may use an optional pinned TypeScript SDK sidecar for its documented interactive lifecycle. This is a compatibility choice, not a mandatory runtime or a second UI implementation. Start it only for the selected provider; the native shell and other adapters work without it. Keep local IPC narrow, versioned, and bounded; compare its actual resource cost rather than assuming a bridge is free.

- One terminal owner; blocking Git/SQLite/filesystem work stays off the rendering path.
- Bounded worker channels; batch stream updates. Preserve output on disk while virtualizing the visible window; do not grow an in-memory transcript forever.
- Invalidate only changed views; redraw on input/state changes, at most 30 fps during streams, never on an idle timer alone.
- Cache parsing/diff results by source identity; avoid reloading the repository or recomputing all hashes per frame.
- Launch commands with direct argv and no implicit shell. Shell execution separately identifies the executable, dialect, and exact shell text; `.cmd`/`.bat` require an explicit shell path, not a silent wrapper. Establish native process-tree ownership before offering safe cancellation: owned process groups on POSIX, Job Objects or an equivalently verified tree-ownership mechanism on Windows. If ownership cannot be established, reject the safe-cancel action rather than advertising it. Track partial output, exit status, and terminal recovery; external-agent cancellation follows its actual protocol, and timeout/forced teardown remains outcome unknown unless tree exit is verified. Never claim that cancellation undoes changes.
- Select context by scope and evidence references; do not inject every form prompt or the full historical transcript. Display provider-reported token counts separately from estimates, identify turn/session/cumulative scope, and disclose provider-added context that cannot be inspected. Do not invent savings percentages or sum incompatible counters.
- Local packet deduplication is structural, never lossy: a capture whose bytes are already present in another selected capture of the same `(root, path, source_sha256)` is emitted as a `same_bytes_as` citation that always resolves to a text-bearing entry — never a citation chain. Codex `edit_baseline` may cite a byte-identical whole-file capture instead of resending it. Distinct paths or revisions with identical text keep separate bytes. Oversized ACP tool observations are bounded by labelled head/tail elision (`truncated_by_eevee`, exact `total_bytes`/`omitted_bytes`) rather than aborting the provider session; receipts and drawers disclose deduplicated counts, and savings are never presented as provider cache hits or billing.
- Use one specialist request at a time initially. No background model chatter, automatic agent fan-out, or model calls for cosmetic transitions.
- Apply the task lifecycle and retention rules above to every persistence path, including command spools and durable memories.

Initial native local-shell performance acceptance targets, not measurements: idle CPU <1% of one core over 60s; idle RSS <=80 MiB; warm local startup to usable UI p95 <=200 ms over 30 runs; local key-to-render p95 <=50 ms under streamed output. Record hardware, release profile, terminal size, sample method, and workload. Report optional SDK bridge and external-agent resources separately **and in aggregate**; a core-only number is not total application cost. Benchmark a 10 MiB output stream and a 10,000-line diff; memory must remain bounded by configured windows/queues. Optimize from measurements, not assumptions.
