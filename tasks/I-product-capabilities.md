# I — Additional product capabilities

GP01–GP05 completed in Waves1–2/6; specifications and scoped proof are in [COMPLETED.md](COMPLETED.md). The five remaining capabilities below are planned only. Reuse the current executor, writer, approvals and receipt authority; [design rules](../docs/DESIGN_RULES.md) remain binding.

Verification for each task: targeted consumer-visible regressions and an actual disposable CLI/TUI journey. Reuse bounded native coverage profiles; do not multiply every case across every architecture or test internal wiring. Live model interpretation requires separate authorization.

### GP06 — Reviewed screenshot input on a supported native route

- [ ] Explicitly attach one bounded PNG/JPEG to a documented image-capable native Responses route.
- **Priority:** 2. **Needs:** —. **Builds on:** C02, C03A, T01A, T01C.
- **Gap:** Current native messages and approved source capture are text-only; binary-source rejection is not image support.
- **Change:** Validate format, compressed/decoded bounds, dimensions and immutable identity. Show disclosure, bytes, selected route capability and retention/purge policy. Respect containment, exclusions, no-link policy and request-body limits. Unknown/unsupported capability refuses rather than silently dropping the image.
- **Accept:** Protocol evidence contains the exact approved image bytes; receipt distinguishes actual serialized bytes from unknown image tokens. Changed/deleted source invalidates dispatch; removal/cancel sends nothing. Exercise restart, quota and purge. Actual model interpretation remains a separate authorized live row.
- **Watch out:** Images can contain secrets that cannot reliably be redacted. Do not claim visual review from a hash when the terminal cannot display the image. No URL fetch, automatic clipboard capture, OCR, PDF/audio/video or all-adapter expansion.

### GP07 — Reviewed selected local Git commit

- [ ] Commit one explicit whole-file changeset locally without silently including other work.
- **Priority:** 3. **Needs:** —. **Builds on:** C01, R01, R02, A03.
- **Gap:** Current repository integration intentionally observes Git read-only. This task requires a scoped design-contract amendment before implementation; this plan does not change that contract.
- **Change:** Ordinary supported repository and initially clean index only. Freeze selected paths/content, HEAD, index, message, identity and configuration effects. Review and bind the exact commit operation to existing consent. Hooks, filters, signing and helpers must be enforceably excluded with disclosure or cause refusal.
- **Accept:** In a disposable repository with two dirty files, commit only the selected file and retain the other unchanged. Existing staged changes, merge state and HEAD/source/index/configuration drift refuse. Record actual commit ID and honest partial index/ref outcomes; a commit is not verification of its content.
- **Watch out:** No push, authentication, branch/worktree management, rebase, conflict resolution, automatic retry/reset or claimed rollback. File approval must not silently authorize repository code execution.

### GP08 — Per-request reasoning-effort analysis for an explicit `auto` effort

- [ ] Resolve each explicitly sent request's reasoning effort from how open-ended its problem is, only when the user selected `auto`.
- **Priority:** 4. **Needs:** GP10. **Builds on:** EV18, EV19, T01C. **Wave:** unassigned; not part of Wave7 and does not start automatically.
- **Gap:** Effort is a fixed per-route/model choice (`/effort`, pairings, preferences). EV18/EV19 classify request capability, not difficulty. Every request therefore bills the same effort regardless of whether the fix is given or the cause is open.
- **Change:** Requires a scoped design-contract amendment for the new `auto` effort value before implementation. Offer `auto` in the reasoning picker and `/effort auto` on every route and model through GP10's route-neutral flow. Where the model exposes no controllable or acknowledged effort, the same preview/receipt shows the classification with `effort fixed by provider; not applied` instead of hiding the step. At explicit submission, after busy/cancellation/approval guards and before the frozen owner/lease/receipt is prepared, one bounded local English/Korean rule table classifies the current user request into `trivial`/`moderate`/`hard` by how open-ended it is (fix or target given → trivial; a few candidate causes or designs → moderate; open cause of flaky/concurrent/stale behavior or easy-to-get-subtly-wrong invariants → hard). Volume of work, politeness and verbosity never raise it; ties choose the lower bucket. Map `trivial→low`, `moderate→high`, `hard→xhigh`, then clamp to the model's advertised ladder without exceeding a ceiling one tier below its top. A standalone lowercase `ultrathink` prose word (not in code spans/fences, paths, identifiers or quoted source) selects the highest advertised effort for that request only. Ambiguity or no matching rule keeps the last resolved effort (initially the model's default). Show the requested `auto`, the resolved effort and the matched reason in the EV19 preview and the request receipt.
- **Accept:** English/Korean fixture requests produce each bucket, the tie-lower rule, the `ultrathink` override and its non-matching forms (`ultrathinking`, `` `ultrathink` ``, `ultrathink.rs`, quoted source), and models with sparse, single or no effort ladders. The EV19 preview equals the resolved effort in actual explicitly submitted loopback protocol evidence and receipts. Typing, paste, browsing, follow-up classification of provider output and EV18 form changes never change the resolved effort or dispatch. Busy/pending work is never reclassified. `auto` and fixed efforts survive restart through existing preference/pairing persistence with older-writer refusal; selecting a fixed effort restores today's behavior byte-for-byte. Report fixture observations for the rule table. Exercise both sizes.
- **Watch out:** No model or judge classifier, extra provider request, confidence/ability score, learned or automatic rule change. Never call the resolved effort observed/applied unless the backend acknowledges it. Never switch provider/model, load a pairing/session, change form or grant anything. Never classify provider output, quoted source, metadata browsing or partner flavor. A model-judge variant (separate judge model, timeouts, usage accounting) is out of scope and would need its own contract amendment plus visible per-request cost and separate live/paid authorization.

### GP09 — Task-owned todo progress that drives automatic form selection

- [ ] Keep the provider's step list for the current request as structured task progress and let Eevee's automatic form follow the adopted active step at explicit send boundaries.
- **Priority:** 4. **Needs:** GP10. **Builds on:** EV18, EV19, EV15, TC02, T01C. **Wave:** unassigned; not part of Wave7 and does not start automatically. GP08, when present, reuses the same active-step input.
- **Gap:** Codex `turn/plan/updated` and ACP `plan` updates already arrive, but only as flat transcript `ItemKind::Plan` text. Claude SDK todo-tool observations are not normalized, and native direct routes have no step tool. Acceptance criteria are user-confirmed verification targets, not progress. EV18 keeps the current form for ambiguous follow-ups ("continue", "next", "계속") even when the remaining work is obviously a different specialty.
- **Change:** Requires a scoped design-contract amendment before implementation, because EV18 currently never classifies provider output. (1) Normalize Codex/ACP plan steps, Claude SDK todo-tool observations and a new native-route Eevee `todo` tool (`init`/`start`/`done`/`drop`/`block`/`unblock`/`append`/`view`, phases, exact-label targeting, a single active step, bounded to 64 steps and short single-line labels) into one task-owned, revisioned progress list using the existing store writer and the Schema19 admission/migration/older-writer-refusal contract. Status changes are provider claims and grant nothing; the tool has no file, command or network effect. (2) An optional native-route eager prelude asking the model to initialize a phased list first is off by default and appears as exact added bytes in the receipt. (3) A provider list stays `proposed` until the user explicitly adopts it on the task card (editable, duplicates flagged, like EV15); a later provider revision of an adopted list shows the diff and needs re-adoption. Routes that emit no step source show the same todo surface as `no step list from this route` through GP10, never a different flow. (4) In automatic mode only, at the explicit send boundary after EV18's busy/cancellation/approval guards: an unambiguous user request still wins; an ambiguous follow-up classifies the adopted list's active step label with the same EV18 rule table instead of keeping the current form. The transition reason names the step. With no adopted active step, today's keep-current behavior applies. The EV19 preview shows the same prediction.
- **Accept:** Actual Codex/ACP/Claude SDK protocol fixtures and a native loopback `todo` tool produce identical structured lists; malformed, oversize, duplicate-label and second-active-step inputs refuse or normalize visibly without losing the transcript text. A three-step adopted list (investigate → fix → verify) moves Eevee through the matching specialists on three explicit `continue` sends, in English and Korean at both sizes, with EV19 previews equal to dispatched receipts. Unadopted lists, manual specialist mode, explicit read-only/Plan/Review requests, busy/pending approvals, typing/paste/browsing and mid-run status changes never change form, provider/model/draft or dispatch anything. Adoption, revision and active step survive restart; older writers refuse; purge removes the list. Completing every step does not check criteria or mark the task complete. Report fixture observations for the rule-table input change.
- **Watch out:** No mid-run form or capability change. Evolution happens only before the next request's frozen owner/lease/receipt. No hidden or automatic continuation: completion reminders or mid-run nudges that re-prompt the model are excluded, because Eevee never sends without explicit user intent. Classify only the bounded adopted active label, never other provider output, quoted source or partner flavor. Provider step status is not evidence. No model classifier, extra provider request or cross-partner chaining.

### GP10 — Route- and model-neutral usage flow

- [ ] Give every provider route and model the same user journey, keys, screens and receipt layout, with capability gaps disclosed in place rather than as a different flow.
- **Priority:** 3. **Needs:** —. **Builds on:** A03, C02, C03A, T01C, EV18, EV19. **Wave:** unassigned; not part of Wave7 and does not start automatically. GP08/GP09 depend on it.
- **Gap:** The same request currently takes visibly different paths by route: controlled Codex Implement forces a fresh thread while Plan/native sessions resume, artifact retrieval exists only on native/Codex, ACP session listing depends on the peer, SDK effort is requested but not acknowledged, step plans are transcript text on some routes and absent on others, and effort pickers appear or disappear by model. Users have to learn each route's flow.
- **Change:** Requires a scoped design-contract amendment that names one canonical journey: connect → choose model/effort → write request → EV19 preview (form, effort, todo step, context) → explicit send → stream → file/command approvals → todo progress → follow-up/`continue` → cancel → resume or new session → handoff. Every route (native HTTP variants, controlled Codex, Claude SDK, OpenCode/Gemini/Devin ACP) and every model renders each step with the same keys, commands, screen order and receipt fields. Adapters normalize into the existing smallest common request/event boundary: messages, tool/file/command requests, approvals, step plans, effort request vs acknowledgment, usage, outcomes. A step a route cannot perform stays in its place with one uniform disclosure (`unsupported on <route>: <reason>`, `requested, not acknowledged`, `unknown`) and the same next actions. Provider-specific semantics remain available in inspection, not as alternative flows. One declarative per-route capability table drives disclosure; no adapter-specific UI branches outside it.
- **Accept:** A loopback/controlled conformance matrix runs the canonical journey on every route with at least two models per route that differ in effort/tool/plan support. Each run yields the same ordered sequence of user-visible states, key hints and receipt field names; only declared capability disclosures differ. A new or unknown model on an existing route follows the same flow with unknown capabilities shown as unknown. Switching provider or model mid-task keeps draft/caret, form, todo list and criteria and shows the same journey. Exercise English/Korean content at both sizes. Live-provider confirmation stays a separate authorized H row.
- **Watch out:** Identical flow is not identical authority. Never fake a capability, silently substitute a route/model, fall back on failure, or widen grants to make flows match. Missing usage/effort/plan stays unknown, not zero or applied. Do not flatten provider-specific identities or semantics away. Disclose them in place. No universal agent framework or new executor, parser, approval queue or receipt authority.
